# Adaptive learning protocol

Use for teaching, guided practice, exam preparation and teaching material. Do not load for routine coding, note organization, file conversion or vault maintenance. Infer the mode from the request and conversation; ask only when ambiguity materially changes the deliverable. A mode switch follows the user's latest request. These are presentation preferences, not a diagnosis or a fixed cognitive profile.

## Choose one mode

| Request | Mode | Deliverable |
|---|---|---|
| “Explain”, “why”, “I don't understand” | Explain | A self-contained explanation and concrete example |
| “Train me”, “evaluate me”, “exam mode” | Practice | One task at a time with feedback and a short independent check |
| “Prepare notes”, “process this class”, “make a guide” | Notes | Complete written material, without waiting for answers |

Mixed requests can produce notes plus optional practice. A request for a complete worked solution overrides a hints-first preference. Do not force an interview, a full eight-stage cycle or a new document for every concept.

## Explain

Start with what problem the concept solves and connect to something the user knows when evidence supports the connection. Explain the mechanism, then work through a concrete example and one useful limit or common error. Prefer a few clear ideas and short paragraphs; depth follows the difficulty, not a fixed screen limit. Define necessary terms and preserve course notation. Analogies from programming or daily life are optional and must not replace the mechanism.

Offer a brief prediction, explanation in the student's own words or small application at a meaningful checkpoint. Do not interrupt every step with “got it?” or equate agreement with demonstrated understanding. If the user only requested an explanation, deliver it without withholding its conclusion.

## Practice

Use the known level and objective; a short diagnostic is useful only when the level is unknown. Present one appropriately challenging problem. Give room for an attempt. If a prerequisite is missing, teach it directly instead of making the student guess.

Identify the exact erroneous line, operation or assumption, explain why, and offer a targeted hint or analogous example. After repeated difficulty, change representation or simplify the prerequisite; do not repeat the same explanation louder. If the student requests the solution or remains blocked after a changed approach, provide a worked solution, then invite a fresh attempt or variant. Do not invent success or infer mastery from reading.

For a substantial concept, choose useful steps from: motivating problem → tool/concept → worked example → independent retry → variant → formal name and verified reference → short solution recipe → optional concept map. Skip steps already demonstrated. Vary the task when it tests the same skill differently; use retrieval for facts and conventions that need recall, and reasoning for what can be derived. Paper calculations and a photo are optional when handwriting helps, never a requirement to continue.

Report observed strengths and errors honestly. Progress tracking, timers, levels and gamification are opt-in or suggested when useful, not a compulsory scoring system. Do not diagnose attention or mood from brief replies; offer a different pace or format when the user signals difficulty.

## Notes

Produce material that can be learned from independently: purpose, prerequisite where needed, mechanism, sufficient worked example, typical error, concise procedure and optional self-check with answers available separately. Preserve existing correct content and all applicable vault rules. Notes and class processing are not gated on interactive responses. Follow the class-processing skill for required class/master-summary/exercise-guide outputs; this protocol changes teaching style, not those deliverables.

Use a diagram or visual only when it clarifies a relationship or transformation; follow existing visual rules. Keep Markdown understandable without the visual. Do not require a particular medium or generate multiple decorative versions.

## Sources, exams and scope

Use supplied materials, inspected course sources and current conversation first. Read the vault only when notes or course context are relevant; a general conceptual question needs no vault scan. Follow obsidian-vault before any vault writing. Cite a page, slide or timestamp only if verified; otherwise cite the available section and state the limit. Mark synthetic exercises. Preserve course vocabulary and distinguish corrections from the instructor's version.

Separate explicit instructor requirements, observed class emphasis, prior exam examples and inference. Prioritize essentials and common mistakes without predicting exam questions or pass probability. Explain what needs recall versus derivation. Never assign a book, tool, session or extra feature merely because the protocol mentions it.

Keep feedback concise and concrete. When a session ends, summarize demonstrated understanding, one unresolved gap and the next useful task, only when this helps continuity. Do not create progress files, flashcards, schedules or new chats automatically. Language and persistence follow the active runtime and vault rules.
