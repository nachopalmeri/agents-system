# Lean execution

## Default choices

- Use the smallest capable available model for routine work; prefer Luna in Standard mode where supported. Keep effort low/medium unless difficulty warrants more. Strong models handle difficult diagnosis, architecture and consequential judgment, not every plan/review.
- Model/speed/MCP preferences are instructions, not proof that client settings changed. Do not override project-required tools, disable active integrations blindly or claim a model switch without a real invocation. The user chooses unsupported UI settings.
- Tiny or tightly coupled work stays direct. Independent non-sensitive work can use the scoped verified-free OpenCode bridge or a smaller native worker. Delegate meaningful chunks, not micro-actions; preparation and verification must be worth the handoff.
- One selected workflow/skill at a time. Reuse approved decisions/specs; grill only material unknowns. Medium/large features use `ticket_sessions.md`; no ceremonial pipeline for small edits.

## Context and review budget

Search paths/symbols first, then read relevant ranges (mandatory instruction files must still be read completely). Send objective, acceptance criteria, exact ownership, exclusions, file pointers and necessary checks; never entire histories or raw logs. Worker results are short conclusions plus evidence and blockers.

Do not duplicate a delegated investigation in the primary. Verify its decisive sources or artifacts instead. Prefer one combined scope/spec/quality review at a meaningful checkpoint; separate reviewers only for demonstrated risk, independent expertise or explicit request. Check every changed artifact, but do not spawn two reviewers per tiny task.

Run relevant tests after changes; run a broad suite at final integration when warranted. Reuse evidence only for unchanged artifacts in the same task; rerun affected checks after edits, dependency/environment changes or stale results. Safety, acceptance criteria and fresh completion evidence are never optional. Each loop is bounded; one worker model attempt by default, then primary replan, not automatic model roulette.

Start fresh at substantial ticket boundaries with a compact handoff; new chats/messages still require explicit authorization. A fresh chat does not reset subscription allowance. Do not fork full history for routine workers.

## Measure before expanding

Use `docs/token-efficiency.md` in the registered repository only when evaluating savings. Globally, resolve the checkout through `~/.agents/local-runtime.json` (`repoPath`); do not assume `~/docs` exists. Record actual model/backend, primary prep/review, retries, provider usage/cost and account allowance before/after when available. Concurrent account activity confounds attribution; unknown values stay unknown. A free worker bill, static tests or shorter instructions do not establish savings. No automatic monitoring, new benchmark infrastructure or paid fallback.
