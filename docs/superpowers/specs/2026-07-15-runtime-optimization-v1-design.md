# Runtime Optimization v1 — Design Specification

**Date:** 2026-07-15  
**Status:** Approved for implementation by the director  
**Branch:** `agente/runtime-optimization-v1`

## 1. Problem

The system contains valuable capabilities accumulated over a long period, but its runtime surface has become larger than the work requires. Simple requests can load broad rules, long workflow documents, multiple agents, validation layers, and incomplete loops. At the same time, several active files point to archived or missing components, installed entrypoints have drifted, and the frontend guidance can reproduce the generic visual patterns it warns against.

The optimization must preserve specialized capabilities while making the default path small, deterministic, portable, and measurable.

## 2. Objectives

1. Establish one vendor-neutral canonical runtime core for local repositories and global use.
2. Support Codex, Claude Code, OpenCode, Devin, Gemini/Antigravity, Cursor, Aider, Zed, and generic CLI clients through thin adapters.
3. Route simple work through a low-context single-agent lane and load specialized knowledge only when evidence requires it.
4. Eliminate active references to missing or archived files without deleting archived knowledge.
5. Give every iterative loop explicit budgets, stop conditions, and outcomes.
6. Connect feedback, lessons, traces, and outcome scoring into a real lightweight harness.
7. Replace generic “AI design” defaults with a subject-grounded visual workflow and screenshot critique.
8. Verify local installation, remote branch state, rollback, and cross-IDE parity.

## 3. Non-goals

- Deleting the archive or reducing the catalog of available agents and skills.
- Automatically installing plugins, MCPs, or credentials.
- Running a multi-agent council for routine decisions.
- Building a hosted orchestration service or a new framework.
- Requiring the user to remember internal workflow names.
- Merging the branch into `main`.

## 4. Design principles

- **Preserve capability, remove automatic load.** A capability may move from preload to discovery without being removed.
- **One source of truth.** Durable behavior is canonical once; adapters must not restate it.
- **Progressive disclosure.** Load metadata first, then the smallest relevant instruction file, then references only when needed.
- **Single agent first.** Delegation requires independent work, material context isolation, or a review that can change the result.
- **Explicit termination.** Every loop has a finite budget and a machine-readable result.
- **Evidence over ritual.** Validation is proportional to risk; a simple edit does not inherit the release process.
- **Portable core, optional integrations.** The core is Markdown, JSON, and PowerShell; vendor-specific behavior remains in adapters.
- **Reversible migration.** No physical deletion is required in v1; previous files remain recoverable in Git.

## 5. Runtime architecture

### 5.1 Canonical source

`.agents/AGENTS.md` is the **only editable policy source** for the compact, vendor-neutral runtime core. It contains only:

- identity pointer and non-negotiable safety boundaries;
- chat-first interaction contract;
- lane-selection rules;
- progressive-loading rules;
- proportional validation and stop conditions;
- pointers to the capability index and durable memory.

It must not duplicate full workflow tutorials, role descriptions, provider-specific syntax, or archived components.

`AGENTS.md` at repository root is generated by `bin/sync-runtime.ps1` from a fixed adapter template plus the SHA-256 of `.agents/AGENTS.md`. It must not contain an independently editable copy of the policy. `bin/doctor.ps1` recomputes the hash and fails on drift. The same rule applies to managed global copies when symbolic links are unavailable.

### 5.2 Runtime manifest

`config/runtime-manifest.json` records:

- canonical entrypoint;
- supported adapter destinations;
- active instruction roots;
- paths excluded from runtime resolution (`archive`, generated output, dependencies);
- optional preload files allowed for clients that support them;
- schema version.

The manifest is operational metadata, not another policy layer. Sync and validation scripts consume it so paths are not duplicated across scripts.

### 5.3 Thin adapters

Vendor files (`CLAUDE.md`, `GEMINI.md`, `.cursorrules`, OpenCode configuration, Aider configuration, Zed settings, and Devin installation targets) contain only:

1. how that client discovers the canonical core;
2. the minimum vendor-specific import/config syntax;
3. no duplicated routing or council policy.

Global installation prefers symbolic links to the canonical installed core. If the platform refuses links, it writes a managed copy with a source hash and the doctor command detects drift.

`bin/sync-runtime.ps1` is transactional: it resolves all targets, validates that they stay inside declared locations, stages generated files, and backs up replaced files with hashes in a timestamped manifest before replacement. A failed replacement restores targets already changed. `-WhatIf` performs no writes. `-Restore <manifest>` verifies backup hashes and restores only files owned by that manifest. Unmanaged local drift fails safe and requires `-Force` instead of being overwritten silently.

### 5.4 Capability index

`workflows/index.md` remains the human-readable discovery map, but it is reduced to intent-to-component mappings and escalation triggers. Long procedures remain in their own files and are read only after routing.

Active files may not reference archived or missing runtime components as if they were executable. Historical references must be clearly labeled as archive documentation and excluded from resolution.

## 6. Progressive loading model

The runtime uses four tiers:

| Tier | Loaded when | Contents |
|---|---|---|
| T0 Core | Every request | compact canonical contract and safety boundaries |
| T1 Route | Intent classification | capability index entry and selected role metadata |
| T2 Execute | A specialized path is selected | one workflow/skill plus directly required references |
| T3 Escalate | Evidence justifies it | parallel agents, high-risk checks, council, or deep research |

OpenCode must not preload the whole workflow library. Its `instructions` list is limited to the canonical core and, where technically required, one compact index. Other clients use the same rule through their adapter.

The sync checker reports estimated character/token pressure for T0 and the OpenCode preload. Thresholds are regression budgets, not exact billing measurements.

## 7. Routing lanes

The router returns this versioned JSON contract:

```json
{
  "schemaVersion": 1,
  "taskId": "string",
  "lane": "SIMPLE|SPECIALIZED|PARALLEL|HIGH_RISK",
  "primary": { "id": "agent-id", "file": "relative/path" },
  "support": [{ "id": "agent-id", "file": "relative/path", "purpose": "review|research|delivery" }],
  "components": ["relative/workflow-or-skill-path"],
  "reasons": ["stable-reason-code"],
  "approvalRequired": false,
  "budgets": { "maxIterations": 3, "maxReplans": 1, "maxAgents": 1 }
}
```

`bin/route-task.ps1` reads a task JSON and applies this precedence: explicit high-risk facts and policy gates; explicit agent mention; explicit user request for parallel/council; specialized intent; simple fallback. High-risk facts cannot be bypassed by an explicit agent mention. Exact trigger tables live in `config/routing-rules.json`, use bounded words or phrases, and are evaluated deterministically. Ambiguous unmatched tasks fall back to `SIMPLE/agente-principal`. More than one simultaneous specialist match remains single-primary by configured priority and records `ambiguous-specialist`; it does not fan out automatically.

### SIMPLE

- Default for explanation, lookup, one-file change, small fix, or direct command.
- One primary agent, no automatic reviewer, no planning ceremony under four meaningful steps.
- Load T0 and only the directly relevant skill/workflow if one is clearly triggered.

### SPECIALIZED

- Used when domain expertise materially changes execution: academic tutoring, Obsidian, SEO/GEO/AEO, product, AI architecture, security, release, or design.
- One primary specialist by default.
- A support role is added only for a distinct deliverable or an independent verification need.

### PARALLEL

- Used only for two or more independent, read-heavy tasks with non-overlapping ownership and useful latency reduction.
- Agent count is capped by explicit budget; simple comparison defaults to at most two support agents.

### HIGH_RISK

- Used for credentials, production writes, payments, external messages, destructive actions, or consequential releases.
- Requires explicit approval where policy demands it and risk-proportional validation.

The portable five-advisor council remains available as an explicit deliberation tool, never an automatic router destination. Regexes use explicit word boundaries and configured phrases only, so substrings such as `pr` in Spanish words cannot trigger code review.

## 8. Loop controller

Every repeated workflow follows a shared state contract:

`perceive -> decide -> act -> validate -> complete | replan | blocked`

Required controls:

- `max_iterations`;
- `max_replans`;
- `max_agents`;
- optional time/context budget;
- success predicate;
- real blocker predicate;
- final receipt.

Default budgets are small and lane-specific. A failed validation may replan once for SIMPLE work and a limited number of times for larger work. Repeated identical failures terminate as blocked instead of silently spinning. “Continue until finished” increases persistence toward the objective but never removes safety or finite iteration controls.

Budget defaults are executable configuration:

| Lane | Iterations | Replans | Agents |
|---|---:|---:|---:|
| SIMPLE | 3 | 1 | 1 |
| SPECIALIZED | 6 | 2 | 1 |
| PARALLEL | 8 | 2 | 4 |
| HIGH_RISK | 5 | 1 | 2 |

A repeated failure is the same normalized `action + target + errorCode` twice without a new observation. A real blocker is a missing permission, unavailable required dependency, user decision with materially different outcomes, or the same repeated failure after the allowed replan. Every iterative active workflow is listed in `config/loop-registry.json`; graph validation fails if it lacks a lane, success predicate, and budget.

The final receipt schema is:

```json
{
  "schemaVersion": 1,
  "taskId": "string",
  "state": "SUCCESS|BLOCKED|NEEDS_USER|BUDGET_EXCEEDED",
  "iterations": 1,
  "replans": 0,
  "evidence": ["command or artifact"],
  "reasonCode": "stable-code"
}
```

## 9. Feedback and evaluation harness

The v1 harness is file-backed and intentionally small:

- `runtime/traces/*.jsonl`: append-only structured events for route, load, action, validation, replan, and result;
- `.agents/tasks/lessons.md`: curated human-readable lessons;
- `.agents/memory/lessons-global.md`: promoted durable lessons only after confirmation;
- `evals/runtime-cases.json`: repeatable routing, reference, loop, portability, and visual-workflow cases;
- `bin/run-runtime-evals.ps1`: deterministic evaluator with a nonzero exit code on regression;
- `bin/record-runtime-event.ps1`: safe event writer without secrets or prompt bodies.

An event contains timestamp, task id, lane, selected components, iteration, status, reason code, and coarse context metrics. It must not store credentials, full conversations, personal document contents, or hidden chain-of-thought.

Events follow `config/runtime-event.schema.json`, are written with an exclusive file handle to one JSONL file per UTC day, and rotate after 30 days. The writer rejects fields outside the schema and values matching the existing secret scanner. Tests launch concurrent writers and assert every line parses. Repository traces are gitignored; only synthetic fixtures are versioned.

Each eval case is pass/fail with an integer weight. The suite score is `100 * passedWeight / totalWeight`; release threshold is 100% for safety/reference/adapter fixtures and at least 95% overall. A task outcome score is reported separately as: objective success 40, validation evidence 25, no director correction 20, stayed inside lane budget 15. Unknown real-world outcomes remain `unscored` rather than being treated as success. The first v1 corpus is the baseline; future releases may not reduce either suite score without an explicit recorded waiver.

Feedback promotion is evidence-based:

1. capture an incident;
2. classify whether it is local noise or repeated failure;
3. reproduce it as an eval case when possible;
4. change the smallest rule/router/test;
5. promote a durable lesson only with human confirmation.

This turns the existing aspirational feedback loop into an executable contract without a background daemon.

## 10. Visual quality workflow

The frontend path uses a compact staged brief before code:

1. **Grounding:** subject, audience, job-to-be-done, brand truth, content hierarchy, constraints.
2. **References:** two or three concrete visual references or moodboard directions; identify what to borrow and what to avoid.
3. **Signature:** choose one memorable visual idea tied to the subject, not a generic effect stack.
4. **System:** concise decisions for typography, palette, spatial rhythm, composition, motion, and 3D role.
5. **Wireframe:** compare at least two structural directions for material pages; use one for simple components.
6. **Implementation:** accessible, responsive, performant code with motion and 3D serving comprehension.
7. **Visual QA:** render real breakpoints, capture screenshots, critique hierarchy/identity/generic-pattern risk, fix, and repeat within budget.

Material pages require screenshots at 390×844 and 1440×900, plus 768×1024 when the layout changes at tablet width. The critique rubric scores 0–2 for subject specificity, hierarchy, composition, typography, color rationale, responsive integrity, accessibility, motion/3D purpose, and generic-pattern avoidance. Each dimension must score at least 1 and the total at least 14/18. Evidence is the brief, reference links or local moodboard, selected wireframe, screenshot paths, rubric, and fixes made; these may live in a task receipt rather than permanent product documentation.

The skill must explicitly reject ungrounded defaults such as interchangeable glass cards, neon gradients, random glow, generic dark dashboards, decorative 3D, and fashionable fonts chosen without subject rationale. This is not a ban on those techniques; they require a defensible connection to the product.

## 11. Compatibility contract

| Client | Status | Minimum capability | Repository entry | Global/CLI installation | Diagnostic |
|---|---|---|---|---|---|
| Codex | stable | `AGENTS.md` discovery | `AGENTS.md` | `$HOME/.codex/AGENTS.md` managed link/copy | `doctor -Client codex` |
| Claude Code | stable | `CLAUDE.md` imports | `CLAUDE.md` importing canonical core | `$HOME/.claude/CLAUDE.md` managed adapter | `doctor -Client claude` |
| OpenCode | stable | JSON instructions | `opencode.json` + compact `instructions` | `$HOME/.config/opencode/AGENTS.md` managed adapter | `doctor -Client opencode` |
| Devin | experimental | repository instruction discovery | repository `AGENTS.md` | legacy/global target only when detected | `doctor -Client devin` |
| Gemini / Antigravity | stable | `GEMINI.md` discovery | `GEMINI.md` / settings | `$HOME/.gemini/GEMINI.md` managed adapter | `doctor -Client gemini` |
| Cursor | experimental | project rules file | `.cursorrules` pointer | project target only | `doctor -Client cursor` |
| Aider | stable | read list config | `.aider.conf.yml` | canonical core path | `doctor -Client aider` |
| Zed | experimental | assistant context config | `.zed/settings.json` | project target only | `doctor -Client zed` |
| Generic CLI | stable | PowerShell 7 | `bin/route-task.ps1`, doctor, evals | repository or installed `.agents` root | `doctor -Client cli` |

Unsupported clients can consume the canonical Markdown directly. Portability tests verify that each declared adapter resolves to the same canonical contract and does not reintroduce archived policy.

Product version numbers are intentionally not pinned because file-discovery support varies independently of releases. The manifest records the required capability shown above and doctor reports `supported`, `unsupported`, or `not-installed` by inspecting the installed client/config; experimental adapters never cause the generic runtime to fail.

### 11.1 Capability reachability

`config/capabilities.json` is the preservation ledger. Every existing agent and active skill has exactly one entry with `id`, `kind`, `mode` (`automatic`, `on-demand`, `explicit-only`, `evaluation`), triggers, component path, and at least one eval fixture id. `bin/check-runtime-graph.ps1` requires 100% of agent-registry entries and active skill directories to be reachable from this ledger. Archived playbooks with unique knowledge are linked as optional references from the corresponding capability; archive files are never preload targets.

## 12. Migration and rollback

Implementation proceeds in three independently testable chunks:

### A. Foundation Runtime

- canonical core and manifest;
- thin adapters and deterministic sync;
- active-reference graph validation;
- compact preloads;
- lane-based router and regression fixtures.

### B. Loop & Learning

- loop budgets and final receipt schema;
- event recording and runtime eval runner;
- repaired lessons/feedback/outcome links;
- session checkpoint and context-degradation contracts where needed.

### C. Visual Quality

- subject-grounded frontend skill;
- reference/wireframe/screenshot critique workflow;
- visual eval fixtures and portability-safe interaction language.

Rollback is `git revert` by chunk. No archive deletion or irreversible migration is part of v1. The previous installed files are backed up before sync, and the installer supports dry-run plus `-WhatIf` semantics.

## 13. Validation and acceptance criteria

The change is ready only when all are true:

1. No active runtime file has an executable reference to a missing or archived component; `pwsh bin/check-runtime-graph.ps1` exits 0.
2. All declared adapters resolve and pass drift checks.
3. OpenCode automatic instructions contain only the compact core/index allowlist.
4. `.agents/AGENTS.md` is at most 6,000 characters and OpenCode automatic instructions total at most 8,000 characters, a reduction of at least 80% from the 51,958-character baseline; `pwsh bin/measure-runtime-context.ps1 -Check` exits 0.
5. A versioned corpus of at least 30 fixtures (minimum 12 SIMPLE, 8 SPECIALIZED, 4 PARALLEL, 6 HIGH_RISK; at least 40% Spanish and 40% English) matches exact lane, primary, maximum agents, approval, and required/forbidden components. SIMPLE fixtures forbid automatic council and reviewer.
6. `pwsh bin/run-runtime-evals.ps1` achieves 100% safety/reference/adapter and at least 95% overall.
7. All iterative workflows expose finite budgets and final states.
8. The feedback harness records sanitized events and fails deterministically on eval regressions.
9. Frontend fixtures require subject grounding, references, a signature, and screenshot critique for material work. Material means a new page or landing with at least three content sections, a component suite, an immersive/3D experience, or a redesign affecting hierarchy; a one-line style fix is non-material.
10. `pwsh bin/validate-agents.ps1`, `pwsh bin/test-system.ps1 -AgentsRoot .agents`, `pwsh bin/release-check.ps1`, and `pwsh bin/check-secrets.ps1` exit 0.
11. In a temporary home, `sync -WhatIf`, `sync`, `doctor`, `sync -Restore <manifest>`, and `doctor` complete without unmanaged drift. The real local install is synced only after the temporary-home test passes.
12. Commits are pushed to `origin/agente/runtime-optimization-v1`; no merge is performed. After push, `git fetch origin agente/runtime-optimization-v1` runs and `git rev-parse HEAD` must equal `git rev-parse origin/agente/runtime-optimization-v1` for the exact verified SHA.

## 14. Known baseline failures to absorb

- `bin/test-system.ps1` incorrectly defaults to a stale global `.agents` copy and reports missing `rules/anti-cemetery.md`.
- `bin/release-check.ps1` expects the wrong Git user name and the branch starts with `ignacio <ipalmeri@uade.edu.ar>` instead of the canonical `Nacho Palmeri <ipalmeri@uade.edu.ar>`.
- Active documents contain missing and archive-directed references.
- OpenCode preloads 26 instruction files, including archived and missing paths.
- Router smoke tests are too weak and over-select roles.

These are migration tests, not reasons to relax acceptance criteria.

## 15. Evidence basis

The architecture follows current primary guidance: maximize a single agent before adding complexity, treat context as finite, progressively disclose instructions, constrain loops with exit conditions, and evaluate repeatable traces and outcomes. Multi-agent execution is retained for tasks whose independence and value justify its much larger token cost. Visual generation is grounded with concrete references, options, and screenshot feedback to avoid high-frequency generic defaults.
